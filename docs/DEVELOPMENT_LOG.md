# EcologicaLite / 生態系シミュレーション 開発記録

この文書は、現在の仕様になった理由を後から追えるように、重要なDecision・検証結果・設計変更だけを残す。全試行・全会話・全runner出力の時系列ログではない。

詳細な旧実験データはGoogle Driveのarchive資産を参照し、現在仕様は `SPEC.md` と `BALANCE.md` を優先する。

## 1. 箱庭シミュレーターとして開始

最初は、64×40のトーラス盤面で植物・草食・肉食・死体を動かし、初期個体数やHP、捕食・繁殖条件を変えながら挙動を観察する私用ブラウザシミュレーターとして開始した。

この段階で得た重要な知見は次のとおり。

- 単発の長期観察だけでは、長寿命の外れ値を「良いバランス」と誤認しやすい。
- 複数seedの一括試験が必要。
- 草食だけを単純に強化しても、結果として肉食の餌が増え、肉食まで強化されることがある。
- 「追う」「逃げる」など役割差を持つ挙動は、単純なHP増加より観察上の意味がある。
- 永久共存そのものを必須目標にはしない。

この時代の64×40、植物300、草食40、肉食8等の値は現在仕様ではない。

## 2. ゲーム化とv1系統

観察用箱庭から、能力を選択して生態系を育てるゲームへ発展した。

主な設計Decision:

- 2 SET × 6 STAGEの12 STAGE構成。
- SET能力と通常能力を分離。
- プレイヤーは個体を直接操作せず、能力選択で介入する。
- 高得点は「食べる → 生まれる → 個体数が増える → さらに食べる・生まれる」という循環拡大から生じるべき。
- STAGE番号による人工的な得点倍率を使わない。
- 得点源を植物摂食、肉食捕食、草食誕生、肉食誕生、草食生存、肉食生存の6系統に整理。

### 得点設計

複数のプレイヤー方針を同一seedで比較し、上手い／手探り／雑で差が出るかを検証した。

途中では絶滅回避ボーナスも検討したが、無絶滅率が高く技能差を薄めるため不採用とした。

得点能力についても、一時は大倍率を試したが、ランダム寄りの選択でも得点能力を多く取得することで循環の弱さを逆転できる問題が出た。このため、得点能力を5種へ整理し、通常3択を「得点能力1枠 + 生態系能力2枠」に固定した。

v1.0では最終的に次を正式確定した。

- 基礎点: 1 / 25 / 25 / 110 / 4 / 10
- 絶滅回避ボーナスなし
- 得点能力5種
- 摂食・繁殖・生存 +15% / stack
- 草食系・肉食系 +10% / stack
- 通常3択 = 得点1 + 生態系2

## 4. v1Rへ分離

v1.0完成後、よりミクロ寄りに「個体を追って見て楽しい」体験へ再設計するため、v1Rを独立系統として開始した。

v1Rは既存のv2構想とは別物。

主な変更方向:

- マップを縮小し、個体を大きく見せる。
- 草食・肉食の移動に休止周期を入れる。
- HP減少を移動そのものから分離する方向を検証。
- 「厳密な均衡」より、繁殖・捕食・循環が見え、盤面が繁栄することを優先。
- マップは実行中の密度で動的変更せず、STAGEごとに事前設定したサイズ系列を使う。

## 5. v1R基礎生態系探索

独立runnerで、能力なしの基礎生態系について広いパラメータ探索を行った。

探索では、最大HP、回復量、初期植物・草食・肉食、肉食移動率、マップサイズ等を多数seedで比較し、Persistence / Reproduction / Predator-prey activity / Balance / Robustnessを分離して評価した。

単一の総合点で自動採用するのではなく、「繁殖・捕食・植物供給が同時に成立する領域」を探す方針を採用した。

この調査過程は `ecosystem-v1R_current.bundle` と関連CSV/JSON/レポートとしてDriveに保存されており、今後のバランス調整時の比較資料として保持する。

## 6. 現行3/6/3系とマップ設計

検証を進め、最終的なゲームでは次の方向へ整理した。

- 草食移動: 3 Turnごと
- 肉食移動: 6 Turnごと
- HP減少: 両種3 Turnごと
- 草食最大HP180、回復34
- 肉食最大HP300、回復100

マップは、SET 1前半28×18を基準に、後半で33×21へ拡張する構成へ縮小した。SET 2も同様に前半30×19、後半32×20の固定系列とした。

初期個体数も見た目の密度と繁殖の立ち上がりを優先して減らし、完成時点ではSET 1が66/6/1、SET 2が75/7/2となった。

## 7. STAGE時間の再設計

v1.0の短いSTAGEをそのまま継承せず、個体の動きを観察できる時間を確保するため再設計した。

最終的に基準を **1 STAGE 25秒 = 100 Turn** とした。

時間延長SET能力は、各SETのSTAGE 1〜6で +1〜+6秒とし、次SETで+1秒へ戻す方式へ変更した。

時間延長は低難度の安定能力ではなく、循環を成立させる難易度が高い代わりに、完成した箱庭を長く回して高い活動量・得点上限へつなげる能力として位置づける。

## 8. v1R得点の再調整

v1.0の得点構造は引き継いだが、v1Rの個体数・繁殖テンポに合わせて基礎点を再調整した。

完成時点のv1R基礎点:

- 植物摂食 1
- 肉食捕食 30
- 草食誕生 20
- 肉食誕生 120
- 草食生存 4
- 肉食生存 15

草食誕生への偏りを弱め、後半に増える捕食・肉食繁殖・肉食生存をより評価する意図がある。

得点能力5種と固定1枠構造は継承した。

## 9. seed・分析基盤

完成前に、バランス調整を後から再現可能にするためseedとログ設計を整理した。

重要なDecision:

- master seedでゲーム結果に関わる乱数全体を決める。
- 能力候補抽選とシミュレーション本体の乱数を用途別に分離する。
- 再生速度、停止、個体選択、オーバーレイ等のUI操作は乱数を消費しない。
- 同じversion・seed・能力選択なら同じ結果を再現する。
- 「やり直し」は同seedでSET 1へ戻す。
- 「最初から」は新seedを生成する。

分析用には、STAGE単位の個体数、摂食、捕食、出生、死亡、植物供給、活動、得点内訳、能力候補と選択等を保持する。

コピーCSVは1 STAGE = 1行を基本とし、Chatへ貼るだけで条件と結果を分析できる自己完結性を優先した。

## 10. スマホUI

機能実装後、GitHub Pagesを使ってiPhone Safariで実機確認を行った。

主なDecision:

- STAGE → 個体数・得点 → 盤面 → 操作 → 下部情報の順。
- 個体選択時にアイコン・ID・HP・HPバーを表示。
- HPバーはアイコンより右から開始し、重ならない。
- 下部はグラフと取得能力を2列で表示。
- 取得能力は最大12個を想定し、SETごとの列として整理。
- 取得能力の説明はスマホtap、PC hover/focus。
- グラフ詳細はSTAGEごとの基本値を表示し、詳細分析値は内部ログへ残す。
- `やり直し` と `最初から` を明確に分離。
- ゲーム終了表示は `GAME SET`。

スマホレイアウトは実機確認後に一度完成基準として固定した。

## 11. PCとスマホの共通化

PC版を別ゲームとして作る案は採用しなかった。

最終方針:

- 同じゲーム状態
- 同じシミュレーション
- 同じ盤面
- 同じDOM・データ
- 同じ能力・HP・グラフ等の基本部品

を使い、PCでは既存要素を3列へ並べ替える。

PCは、左にSTAGE・個体数/得点・グラフ、中央に盤面、右に取得能力・HP・再生・リスタートを配置する。

## 13. 再生速度の最終変更

開発完了直前に、2×をほぼ使わないことから速度構成を見直した。

最終値は **1× / 4× / 8×**。

- 1×: 個体の動きを観察
- 4×: 通常の高速進行
- 8×: 結果を早く進める

8×でも論理Turnをスキップせず、時計が必要なTurnまでシミュレーションを進める。

## 15. 正本化後のコード整理課題

開発速度を優先したため、現在のGitHub実装には `ui-v11.js` 〜 `ui-v21.js` のような段階的UIパッチが残っている。

今後のコード整理では、ゲーム結果を変えずに次を行う予定。

- UIパッチ群を正式なHTML/CSS/JSへ統合
- 重複CSSと上書きCSSの整理
- `preview.html` の変換・パッチ処理の削減
- PC/スマホ共通DOM構造の清書
- prototype・不要ファイルの整理
- 未使用コードの確認

正本化中に確認した既知の整理事項として、`game-info-v19.html` の静的文面には旧速度 `1× / 2× / 4×` が残り、現在は `ui-v15.js` が読み込み時に `1× / 4× / 8×` へ置換している。実際のゲーム表示・動作は現行速度に一致するが、コード整理時には二重管理を解消する。

コード整理ではRNG、能力、得点、生態系、seed結果を変更しない。整理前後を同一seed・同一能力選択で比較し、結果一致を確認する。

## 16. コード統合方針

完成状態を壊さないことを最優先とし、UI整理は一度に全面置換せず段階的に行う。

### 統合の原則

- 生態系、RNG、能力、得点、SET/STAGE進行のロジックは原則として書き換えない。
- PCとスマホは引き続き同一ゲーム状態・同一データ・同一基本部品を使う。
- ファイル数を減らすこと自体を目的にせず、後付けpatchと二重管理をなくすことを目的とする。
- 各段階で動作確認できる状態を維持し、最終確認前に旧patch群を削除しない。

### 実装順

1. `preview.html` が行っている確定済み変更を元実装へ戻す。対象は整数得点表示、1×/4×/8×、pause/再生操作、runtime session参照等。文字列置換でJavaScriptを書き換える方式を解消する。
2. `game-info-v19.html` の旧速度表記を正式値へ修正し、読み込み時の置換を削除する。
3. `ui-v11.js` と `ui-v14.js` の確定した表示・結果・能力説明処理を正式UI処理へ統合する。
4. `ui-v15.css` と `ui-v16.js`、`ui-v17.js`、`ui-v19.js` のスマホ向けCSSを一つの正式CSSへ整理する。
5. `ui-v18.js` と `ui-v20.js`、`ui-v21.js` のPCレイアウトを一つの正式PC処理/CSSへ整理する。必要ならレスポンシブ時のDOM移動処理自体は残してよいが、版番号patchとしては残さない。
6. 上記統合版を現在のiframe構成のまま動かし、旧版と同一seed・同一能力選択で結果を比較する。
7. 結果一致とPC/スマホUI確認後、`index.html → iframe → preview.html` の外側wrapperが不要か判断する。iframe廃止は最後に行い、前段のUI統合とは分離する。
8. すべて確認後に `ui-v12.js`、`ui-v13.js`、prototype、`play-gameset.html`、統合済み `ui-vXX` 等を削除する。

### 完了判定

- 同一seed・同一能力選択でSTAGE結果、個体数、イベント数、得点、CSVが整理前と一致する。
- 1×/4×/8×、pause、個体HP、能力説明、グラフ詳細、コピー、やり直し、最初から、SET2遷移、GAME SETが動く。
- PCとスマホの完成レイアウトが維持される。
- `preview.html` がJavaScriptソース文字列を検索・置換しなくても動作する。
- `ui-vXX` の連続上書きなしで完成UIが成立する。

バランス変更はこの整理工程へ混ぜない。必要なバランス変更はコード整理完了後に別工程として行う。

## 18. バランス診断runnerと草食一時投入の調整

2026-09-04、完成後のバランスを大きく崩さず診断するため、現行 `index.html` のruntimeを直接使う診断runnerを追加した。8種のSET1能力を軸に、狙いビルド、一時投入優先、植物+12優先、草食一時投入優先、一時投入なし、得点優先、混合の方針を同じseed群で比較する。runnerは自動でバランス値を採用せず、問題候補を見つける用途に限定する。

30seed比較では、草食一時投入+2は植物+12優先より全体に見劣りしたため、+3を仮設定して同条件で再比較した。+3では草食一時投入優先の平均得点と植物+12への勝率が改善した一方、植物+12を一律に上回る状態にはならず、双子や肉食察知など相性のある構成で価値が上がった。これを踏まえ、草食一時投入は **取得時 +3** を正式値とした。

SET能力については、平均得点だけで一律評価しない。植物察知・危険察知は得点上限が低めでも、摂食安定・草食生存・捕食抑制といった役割差を持つため、今後も経路・絶滅・捕食・繁殖を併せて判断する。
